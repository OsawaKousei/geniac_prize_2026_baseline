# エージェント共通の実行ルール

このリポジトリを操作する Codex、Claude Code、Antigravity、Cursor に共通して適用する。
作業前にこの文書と [CONTRIBUTING.md](../CONTRIBUTING.md) を読み、チュートリアルの操作には
[ローカル開発と Slurm 実行](tutorial/local_remote.md) を使う。

## 依頼の範囲と実行場所

- 既定は非侵襲的な操作。最新の依頼と継続中の許可から、変更・接続・ジョブ投入の範囲を判断する。
  許可済みの作業を段階ごとに再確認しない。「計画のみ」「実行しない」「ローカルまで」の指定を守る。
- 説明・調査・指示ファイルの追加だけを依頼された場合、それを転送、環境構築、学習、削除の許可に広げない。
- ローカル PC では編集、軽量テスト、lock 生成・検査、梱包・計画を行う。
  検証のために GPU 用ライブラリ全体やモデル本体をローカルへ取得・導入する場合は、その依頼範囲を確認する。
- ログインノードでは軽量な閲覧、SSH の中継、Slurm の操作だけを行う。
  **ログインノードへのアプリケーションのインストール・ダウンロードは禁止**。
  uv、Python、pip パッケージ、VS Code Server、AI エージェント、同期エージェントも対象。
- リモートのコード受信・展開、Git clone/fetch、依存・モデル・アセットの取得、変換、重いコピーやハッシュ計算は、
  GPU を使わない処理も含め、`srun` / `sbatch` で割り当てた計算ノード内で行う。
  `ssh <接続先> 'uv sync ...'` のようにログインノードで構築しない。
- GPU が必要な処理には Slurm で GPU を明示的に要求する。計算ノードへ直接 SSH して割当を回避しない。
  ジョブ内では Slurm の GPU 割当を引き継ぎ、他の GPU を見えるように書き換えない。
- エディタと AI エージェントはローカルで使う。リモートに常駐サービスを追加しない。

## 通常の操作経路

入口は `python3 scripts/remote.py <操作>`。VS Code タスクも同じ入口を呼ぶ。

| 操作 | 実際に行うこと |
| --- | --- |
| `init` | 個人設定をローカルに作成。既存設定は上書きしない |
| `prepare` | ローカルでソースを梱包。CaP-X の取得元によってはローカルから Git 接続する |
| `plan` | ローカルで転送先・容量・ジョブのコマンドを表示・保存。SSH は行わない |
| `setup` | SSH 接続し、CPU 計算ノードで受信・展開後、環境構築ジョブを投入 |
| `check` | GPU 検査ジョブを投入。モデルサーバーや trial は開始しない |
| `submit <段階>` | 収集・変換・SFT・評価のジョブを投入 |
| `status` / `logs` | SSH 経由で投入済みジョブの状態・ログを読む |

- 転送・投入の前に個人設定と `plan` を確認する。コードや設定を変更したら `prepare` → `plan` をやり直す。
- `setup` → `check` → `collect` → `convert` → `sft` の順に結果を確認する。
  必要に応じて `eval-base` / `eval-sft` を追加する。起動・投入できたことを処理成功と扱わない。
- `setup` は受信のための CPU 割当を待つ場合がある。待機中に同じコマンドを重ねて実行しない。
  端末が切れた場合も、保存済みジョブ ID、`status`、ログを先に確認する。
- `--retry` はスクリプトが認める失敗終了済みの最後の段階に使う。待機・実行中のジョブを再投入しない。
  初期設定の試行数・GPU 数・実行時間を、動かないことを理由に無断で大きくしない。
- 失敗した段階の後続を進めず、終了状態と原因を確認する。スクリプトのロック、依存関係、チェックを回避しない。
  ジョブ操作は本人の対象ジョブに限定し、他メンバーのジョブや共有の割当設定を変更しない。

## ファイルと共有領域

- 接続先、アカウント、ユーザー名、パス、ポート offset、資源指定は `.remote.local.json` に保持する。
  特定のマシン・個人の値や認証情報をコード・共有設定・コミット対象の文書へ埋め込まない。
- `.remote.local.json`、`.remote-build/`、`tmp/` は個人用。認証ファイル、`.env*`、個人 venv、モデル、
  データ、実験結果を転送物や Git に混入させない。秘密情報を含むファイルや環境変数を一括表示しない。
- 共有モデルは公開済みの固定 revision を参照する。共有モデルを `HF_HOME` や書込みキャッシュにしない。
  venv、キャッシュ、ログ、データ、adapter は本人の領域へ保存する。
- 共有資産の公開・更新は、その作業自体が依頼されている場合に限定する。
  共有モデル、台帳、他メンバーのディレクトリやキャッシュを通常のセットアップで変更しない。
- 既存 release・収集結果・学習出力を上書きしない。実行中の release 内のコード・venv も編集しない。
  変更はローカルで行って新しい版として配置する。
- 削除は明示的に認められた対象だけに限定する。実パス、所有者、symlink、実行中ジョブからの参照を確認する。
  旧環境を整理する際、同じ個人ディレクトリ配下に新しい環境がないか確認する。
  個人ルート全体の削除、共有領域への再帰的な権限変更、同期の `--delete` を安易に使わない。
- `port_offset` は予約ではない。チーム内調整と実行時の競合検査を守り、競合プロセスを勝手に停止しない。

## uv と固定依存

- 学習用は `remote_tutorial/envs/base/`、vLLM 用は `remote_tutorial/envs/serve/` の
  `pyproject.toml` / `uv.lock` を使う。独立した環境を共通 workspace や一つの venv に統合しない。
- 通常構築は `uv sync --locked`。lock 不整合は保守時にソースと lock を合わせて修正する。
  実行を通すために lock を削除したり、その場で最新版へ解き直したりしない。
- 学習用の固定条件は `requirements-train.txt` と一致させる。ベースライン本体の設定と GPU 用プロジェクトの役割を保つ。
- Robosuite は固定 CaP-X 側の `uv.lock` を `uv sync --frozen --extra robosuite` で使う。
  CaP-X の commit とパッチは既存の `patches/geniac_prize/setup.sh` の指定に従う。
- uv、Python、追加 NVRTC の版は `remote_tutorial/versions.json` を参照する。
  B300 対策を外したり、NVRTC 対策のために固定 Torch の依存を置き換えたりしない。
- Robosuite の既知の依存警告は監査に記録する。未知の不整合、CUDA エラー、サーバー障害を成功扱いで無視しない。

## データと検証結果

- 初期対象は Robosuite `cube_restack` の少数試行と短い SFT。全タスクの学習や提出まで自動で広げない。
- Robosuite の収集 seed は 301–400。train は 301–390、validation は 391–400、評価は 401–450。
  評価用 seed を学習に流用しない。学習前後の比較には同じ評価 seed を使う。
- SFT には成功例を使い、train / validation の両方が必要。少数試行で成功例が不足したら、その事実を報告する。
  架空の成功例を作る、失敗を成功に書き換える、validation を無効にして通す、といった対応はしない。
- 変更時の検査は CONTRIBUTING.md に従う。既存のローカル開発環境を使い、GPU を要しない検査を先に行う。
- ローカルのテスト・lock 検査・dry-run、ジョブの受付、GPU 検査、実 trial、学習完了を区別して報告する。
  過去の別環境の結果を、新しい版の実行成功の証拠にしない。少数試行の結果から性能改善を断定しない。

これらはエージェントへの指示であり、OS・SSH・Slurm の権限制御を置き換えるものではない。
